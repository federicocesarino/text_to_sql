# Text-to-SQL on Synthetic Patient Data

A tool for asking questions about patient data in plain English. Questions are translated
into SQL by Claude, run against a SQLite database, and answered with the query, its
assumptions and the results.

The project uses the [Synthea](https://synthetichealth.github.io/synthea/) 1K synthetic
patient dataset. No real patient data is involved.

> **Status:** work in progress. The dataset, derived tables, eval set and spec are in place.
> The application and the automated eval script are not built yet. See [Roadmap](#roadmap).

## How it works

```
question → prompt (data dictionary + conventions) → Claude API → SQL
         → safety check → read-only SQLite → results + assumptions + explanation
```

1. The user asks a question in English
2. Claude receives the question with a description of the database and generates SQL,
   stating any assumptions it made
3. The SQL is validated: only a single read-only query is accepted
4. The query runs on a read-only connection with a row limit and timeout
5. The user sees the SQL, the assumptions, the result table and a short explanation

Accuracy is measured against a hand-written eval set (see [Evaluation](#evaluation)).
Full design in [docs/spec.md](docs/spec.md).

## Setup

Clone the repository and create a virtual environment:

```
git clone https://github.com/federicocesarino/text_to_sql.git
cd text_to_sql
python3.12 -m venv .venv
source .venv/bin/activate
```

Download the **Synthea 1K sample in CSV format** from the Synthea downloads page and place
the CSV files in `data/`.

## Loading the data

```
sqlite3 labsql.db
```

Then, inside SQLite:

```
.mode csv
.import data/patients.csv patients
.import data/encounters.csv encounters
.import data/conditions.csv conditions
.import data/observations.csv observations
.import data/medications.csv medications
.read queries/01_lab_results.sql
```

This creates `labsql.db` with the five raw tables and a derived `lab_results` table
containing numeric observations with values cast to `REAL`.

## Database overview

| Table | Content |
|---|---|
| `patients` | Demographics, birth and death dates |
| `encounters` | Visits and their type |
| `conditions` | Diagnoses, with start and stop dates |
| `observations` | Measurements and survey answers, all values stored as text |
| `medications` | Prescriptions |
| `lab_results` | Numeric observations only, with `value_num` as `REAL` |

### Known data issues
These produce wrong results without raising any error:

- **All raw values are text.** Numeric comparisons on `observations.VALUE` compare strings
  (`'99' > '126'` is true). Use `lab_results.value_num`.
- **Empty cells are `''`, not `NULL`.** For example, living patients have `DEATHDATE = ''`.
- **`LIKE` is case-insensitive in SQLite.** `LIKE '%diabetes%'` also matches *Prediabetes*.
  Prefer exact matches on `DESCRIPTION`.
- **Synthetic data is cleaner than real data.** For example, every patient with glucose
  ≥ 126 mg/dL already has a diabetes diagnosis, and HbA1c values are not clinically
  realistic in this sample.

A load script that fixes the first two issues at the source is planned.

## Evaluation
[eval/eval_set.md](eval/eval_set.md) contains 10 questions with reference SQL and expected
results, in three difficulty levels:

- **Easy:** single-table counts
- **Medium:** joins, date filters, ranking with ties
- **Hard:** clinically ambiguous questions (latest reading per patient, ESC 2024
  hypertension thresholds, patients never diagnosed with a condition). Each one documents
  the interpretation used.

The planned eval script will run each question through the system, execute the generated
SQL and compare the result with the expected one.
